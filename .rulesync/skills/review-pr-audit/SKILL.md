---
name: review-pr-audit
description: |
  Fetch a PR's diff and risk-review it across docs, architecture, and code
  quality, mindful of token budget.
  Uses gh pr checkout to fetch the PR branch for reproducibility.
  Posts inline comments and an overall verdict via the GitHub Review API in
  a single batch.
  Takes a PR number (e.g. 3) as its argument. Posting a comment on the PR
  requires explicit instruction in the same prompt (e.g. "comment on the PR").
---

# PR Quality / Risk Review

Review PR **#$ARGUMENTS**.

## Input (posting a PR comment)

- By default, only report back in chat.
- Only post a comment to the GitHub PR when the **same prompt** includes one
  of: `post comment` / `comment on pr` / `post to pr`.

---

## Step 1: Check the working tree (required before checkout)

```bash
git status
```

- If there are uncommitted changes, **do not run `gh pr checkout`**. Get to a
  clean state before resuming.

---

## Step 2: Check out the PR branch (required)

```bash
PREV_BRANCH=$(git branch --show-current)
gh pr checkout $ARGUMENTS
git branch --show-current
gh pr view $ARGUMENTS --json headRefName -q .headRefName
```

---

## Step 3: Extract diff and CI checks (token-light)

To keep token usage down, exclude generated/lock files from the diff:

```bash
BASE=$(gh pr view $ARGUMENTS --json baseRefName -q .baseRefName)
git fetch origin "$BASE" 2>/dev/null || true

# Lightweight diff: exclude lockfiles and generated artifacts
git merge-base HEAD "origin/$BASE" | xargs -I{} git diff {}...HEAD -- . \
  ':!requirements/*.txt' ':!*.lock' ':!*.min.js' ':!**/*.svg'
```

Also check:

```bash
gh pr checks $ARGUMENTS
gh pr view $ARGUMENTS --json title,body,commits,files
```

---

## Step 4: Build the audit report and run the evaluation process

Analyze the `git diff` and related files from the following angles and
produce an audit report in chat.

### 1. Review angles and evaluation procedure

- **Purpose/implementation alignment**: does the actual code change match
  the PR title, description, and linked GitHub issue?
- **SSOT/doc sync**: has the change left behind stale docs? In particular —
  `docs/v100_fallback_archtecture/sm70_op_compatibility_matrix.md` and
  `docs/v100_fallback_archtecture/v100_adapter_archtecture.md` (if the
  change touches `csrc/v100_adapter/` or V100 dtype/attention fallback
  logic — see the `v100-csrc-adapter` rule's review checklist),
  `docs/models/supported_models.md` (if the change adds/changes a model
  architecture). Note that `docs/`'s navigation is auto-generated by
  `mkdocs`'s `api-autonav`/`gen-files` plugins (see `mkdocs.yaml`), so there
  is no manual nav/index file to keep in sync — only the content itself.
- **Code quality and robustness**: exception handling, type annotations
  (especially `from __future__ import annotations` ordering, which has
  bitten this fork under PyTorch 2.6 schema inference — see CLAUDE.md),
  boundary checks, security risks (leaked credentials, use of deprecated
  APIs), and — for anything under `vllm/model_executor/models/**` or
  `csrc/v100_adapter/` — compliance with the `v100-csrc-adapter` rule (no
  `getattr`/`hasattr`/dtype-branching in model files; sm_70 op fallbacks
  belong in the C++ adapter, not Python).

### 2. Verdict (Event) criteria

- **REQUEST_CHANGES**: a serious bug, a security hole, a clear mismatch with
  docs/spec, or a violation of the `v100-csrc-adapter` rule.
- **APPROVE**: behavior and structure are sound and remaining points are
  minor comments or small polish items.
- **COMMENT**: mainly open questions or spec clarification needed.

### 3. Output format (use this heading order)

#### 1. Change summary and alignment with stated purpose

#### 2. Docs/architecture evaluation (SSOT)

#### 3. Code quality, tests, and dependencies

#### 4. Inline findings (Critical / Middle / Minor)

- Each finding states a concrete `path` and `line`.
- **Hard constraint**: per the GitHub Review API, an inline comment's `line`
  must be a line that is **added or changed (a `+` line) in this PR's diff**.
- Findings about unchanged surrounding code or deleted lines must not be
  submitted as inline comments — fold them into "5. Overall verdict" or the
  review's summary `body` instead.

#### 5. Overall verdict / recommended action (APPROVE / REQUEST_CHANGES / COMMENT)

---

## Step 5: Batch-post the Review to GitHub (opt-in only)

Only run this if one of the keywords (`post comment`, etc.) was present.

1. **Review payload (JSON) construction policy:**
   - Populate the `comments` array with **only line numbers that appear in
     the PR's diff `+` lines**.
   - A line number outside the diff causes an API error — drop that finding
     from `comments` and fold it into the `body` text instead.
   - For a newly added file, every line in the file is a valid target.

   ```json
   {
     "body": "## PR Quality / Risk Review Summary\nOverall verdict: APPROVE / REQUEST_CHANGES\n...",
     "event": "COMMENT",
     "comments": [
       {
         "path": "vllm/entrypoints/openai/api_server.py",
         "line": 15,
         "body": "[Critical1] Missing exception handling here — recommend adding a try/except."
       },
       {
         "path": "docs/v100_fallback_archtecture/sm70_op_compatibility_matrix.md",
         "line": 42,
         "body": "[Middle1] This row's fallback status looks stale relative to the new adapter op — please update it."
       }
     ]
   }
   ```

2. **Post it in one shot via the GitHub Review API:**

   ```bash
   REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
   gh api -X POST "repos/${REPO}/pulls/$ARGUMENTS/reviews" --input /tmp/review_payload.json
   rm /tmp/review_payload.json
   ```

3. Include the PR URL and a link to the posted review in the final report.

---

## Final report

- Current branch after checkout
- PR URL
- Overall verdict and risk level (low / medium / high)
- Number of inline findings posted, and a link to the posted review
